# Knowledge Base module — agent notes

Product and UI conventions for **knowledge-base** only. Repo-wide AI/runtime rules: [ai-product-conventions.md](../../docs/content/dev/conventions/ai-product-conventions.md).

## Copy & search (user-facing)

- For Knowledge Base search, use **Postgres/Supabase full-text search**; user-facing copy should say search or full-text search, not BM25.
- Engenty-wide breadcrumbs use slash separators, not `>`; use `kbKnowledgeBaseRootCrumb` and compact pickers for KB breadcrumbs.
- Article detail chrome should follow the **offers**-style inline-field pattern for tags and header metadata. Admin lists for articles and FAQs should mirror contacts/offers list UX.
- **KB sidebar (top):** omit redundant “Ihre Wissensdatenbanken”-style labels; show the current KB in a compact picker (dropdown when multiple exist); show the in-menu search box once there are at least `KB_SWITCHER_SEARCH_THRESHOLD` (= **3**) knowledge bases (see `kb-switcher-popover.tsx`); show only the KB name when there is exactly one; align picker height with the adjacent search field.
- In open module secondary nav, the module icon stays in the sidebar rather than moving into the breadcrumb; active nav/list rows rely on typography instead of a filled/accent background.
- **Multi-KB hub breadcrumb (`KbBreadcrumbPicker`):** the chevron sits inline after the KB label (it does not push the trail separator) and rests at `opacity-50`, brightening to `opacity-100` on `group-hover/picker` and while the menu is open (`group-data-[state=open]/picker`) — see the `defaultTrigger` in `kb-switcher-popover.tsx`. The sidebar-header switcher (`KbShellKnowledgeBaseLinks`) instead starts the chevron hidden (`opacity-0`) when the secondary nav is pinned open and reveals it on hover/focus/open.

## Planning & specs

- For Knowledge Base (and similar) UI plans, spell out concrete controls, layout, empty/loading/error states, and Notion-style density; anchor to `SettingsFormSection` and module settings routes — thin one-line UI specs are insufficient.

## Sources, articles, metadata

- **Sources / Daten-Quellen** is the unified ingestion concept (the former “Inbox” is merged in). A single uploaded file/folder or ingested URL is a **source**; each source may have multiple **source-items** (parsed content, PDFs, etc.). Supported source types: URL, Firecrawl URL, Sitemap, Web Index, File Upload, Manual Entry.
- Primary **Add source** (adapter chooser) belongs in the module topbar via `KbModuleShellActions` `primaryAddMenu`, not duplicated in the list toolbar. KB inbox items have **no trash bin** — deletes are permanent.
- Source adapter creation may use a two-step in-dialog index flow: step 1 label **Indexierung starten**; step 2 filterable checkbox list with all items selected by default; select/deselect visible controls; unchecked items marked ignored; source creation starts retrieval.
- Source detail tabs: **Einstellungen** (includes scheduler), **Einträge** (source items), **Logs** (Letzte Läufe / run history); do not use **Ausführen** as a tab label.
- Source item detail: parsed markdown at full width (no column wrapper for the label); raw **Markdown** and **HTML** tabs sit outside the card at the top-left (replacing the “Inhalt” label); no double/stacked cards. Source item metadata: one clean list — no empty placeholder blocks; explanations behind tooltips; lower-priority rows behind **Show more**; inbox ID linked in the list.
- KB breadcrumb picker on source/item detail: switching KB must navigate to the **target KB’s sources list** (not the same sourceId/itemId, which triggers canonical-URL `useEffect` and redirects back). **Source adapter edit** reuses the same card wrappers and field layout as the create adapter dialog.
- Article **summary** reads as a muted lead intro above the main body; edit form order: sources → questions answered → summary → TipTap.
- Article detail metadata panel: show only pinned properties (`show_in_compact: true`) by default; unpinned rows collapse behind an animated **Show more** toggle; avoid extra padding or heavy bordered wrappers around the metadata section.
- **Article tag chips (inline editor):** no separate save step (writes flush on change), no title/description in the add-tag modal, chip background is **darker** (not lighter) than the surface, hover state uses the **primary** color and a **wide** dashed-outline ring, and the edit modal opens **only via the pen icon** (not by clicking the chip itself). Tag row must reserve **stable vertical height** so adding the first or removing the last tag does not shift the article layout.
- **Comments:** flat `article_comments` rows; policy `comments_mode` on KB (`none|enabled|closed`), category/article (`inherit|none|enabled|closed`) with resolver walking the category parent chain (same inherit pattern as templates). Detail page shows a thread below the body when effective mode ≠ `none`; compact metadata shows a comment-count chip linking to `#article-comments`.
- **Article lifecycle UI:** user-facing **Approved** label maps to DB `status: published`; **Locked** is `locked_at` (overrides draft/approved chrome). Sidebar tree shows a leading lifecycle dot before the title; detail title badge opens a lifecycle menu (verify, archive, lock); overflow ⋯ menu keeps the same actions with **Verify content** / **Inhalt verifizieren**. Locked pages block content/metadata updates and metadata refresh.

## Categories & sidebar tree

- **Categories restored** as a hierarchical folder-style taxonomy (`module_kb.categories`, restored in `20260526180000_plugin_kb_categories_restore.sql` after the May 14 removal). Every KB ships a built-in **`general`** category; every article belongs to **exactly one** main category for now.
- **Category view pages** (`ui/pages/category-detail.tsx`) — `cover` (same picker as KB hub: color / gradient / image via vault + Unsplash + AI routes), `cover_inheritance` (`none` | `direct_articles` | `all_children` — controls inherited `effective_cover` on article detail GET), legacy `intro_json`/`outro_json` columns (migrated read-time into blocks), `view_type` (`collection` | `folder`), and `page_settings.blocks` jsonb for configurable page blocks. **Hub start page** uses the same block model via scoped KV `kb.page_layout` (merged on `KnowledgeBase.page_layout` in API responses). Block types: **content** (TipTap), **categories**, **articles**, **faqs** — add/reorder/hide in edit mode (`KbPageBlocksEditor`). Hub keeps fixed chrome: cover/header + search. Sidebar collection sort remains `page_settings.collection` (separate from page blocks).
- **KB sidebar tree (folder view):** show the **category tree above the pages**; do **not** render page icons in the tree (too disturbing); **article (page) rows** always show their **expand/collapse chevron** when a row has children (don't gate it on hover); **category rows** keep the **leading icon at rest and swap to the chevron on row hover/focus** (`SidebarRowLeadingIcon` default — do **not** pass `alwaysShowChevron`); icon swap follows `view_type` — `"folder"` renders **`Folder`** (manually arranged page tree) and `"collection"` renders **`LayoutList`** (auto-sorted list per `page_settings.collection`); the **plus icon next to the filter** opens an add menu with **Add Category** / **Add Page**; sub-category / sub-page creation uses a modal with a **title** input plus a **parent category dropdown**.
- **Drag-and-drop reorder:** Category rows always expose a grip handle (`KbSidebarCategoryReorderDrag` in `category-tree/category-tree-rows.tsx`). Category-on-category drops use a **three-zone placement** (`KbSidebarCategoryDropPlace = "before" | "into" | "after"`): the top ~22% / bottom ~22% are sibling zones (renders `SidebarListInsertDropBar`); the middle ~56% is a re-parent zone (renders a primary-tinted outline ring on the target row). `"into"` flips `parent_id` and appends to the new parent's children; `"before"` / `"after"` reorder under the existing parent. A cycle guard rejects dropping a category onto its own descendant with a toast. Optimistic cache update re-stamps `sort_order` across destination siblings + old siblings (when changing parent), then fires one `updateCategory` per affected row in `Promise.all`. After a successful `"into"` drop the destination branch is auto-expanded so the moved row is immediately visible. **Article (page) rows** expose a grip and accept drops only when their bucketing category's `view_type === "folder"` (the `isReorderable(article)` callback on `KbSidebarArticleManualReorderDrag` — `"collection"` categories auto-sort by `page_settings.collection.sort_by` and must not surface a grip); the grip is **not** gated on global `prefs.sortBy` anymore — dropping in non-manual modes still patches `sort_order`, but the user only sees the new order after flipping the sidebar sort to manual. Dropping an article on a category row patches `category_id` (single-zone full-row drop, no insert bar). The category row owns its own `onDragOver` / `onDrop` (does **not** use `SidebarRow.listInsertDrop`) because the helper only supports two sibling places — `SidebarListInsertDropBar` is rendered manually.
- **Sidebar live cache:** `module_kb.articles` and `module_kb.categories` are published to `supabase_realtime` (`20260527093000_plugin_kb_realtime.sql` + scripts/check-live-cache-security.mjs allowlist). `KbSidebar` wires `useLiveCache` with `createKbSidebarLiveBindings(kbId)` (in `ui/kb-live-cache.ts`) keyed by `currentTenant.id`; postgres row payloads with a different `kb_id` are filtered out, others invalidate `kbCategoryKeys.list(kbId)` or `kbArticleKeys.all`. Realtime is a signal — full data still flows through the Hono API on refetch. After this migration run `pnpm db:migrate && pnpm supabase:restart` so PostgREST picks up the new authenticated grants.

## Data model & integrations

- Article bodies and per-KB settings are canonical in Postgres (Supabase), not a folder-first Markdown file store; Obsidian co-use needs export/sync or an API bridge, not Obsidian Sync alone.
- Per-KB settings live at `/module/knowledge-base/kb/<slug>/settings` (e.g. `default`), not only global app settings.
- Web ingest (URL / Firecrawl / Sitemap / Web Index) uses `@engenty/web-ingest`: raw URL capture and fetch-to-markdown before semantic article generation. For sitemap/web HTML extraction, `auto` selector mode means LLM-generated include/exclude CSS selectors from samples, not merely default cleanup. Filter cookie/search chrome such as `.BorlabsCookie` and `role=search` before markdown generation.
- `FIRECRAWL_API_KEY` is required for hosted Firecrawl; `FIRECRAWL_API_URL` is optional for self-hosted bases.
- Embedding catalog: `packages/ai-core/data/supported-embedding-models.json` (refresh with `pnpm --filter @engenty/ai-core embedding:update`); exported as `supportedEmbeddingModels` from `@engenty/ai-core`. Changing the embedding model in KB General settings triggers full reindex: confirm → progress → toast UX.
- Planned graph route: `/module/knowledge-base/kb/:slug/graph` (Sigma.js + Graphology); edge types: hierarchical parent→child and wiki-link/backlink.
- **`kb_entities` / `kb_relationships` substrate (planned, not yet wired):** the cross-module typed entity store is `@engenty/context-graph` (`context_graph.entities` / `context_graph.edges`, tenant-only RLS, current state only — no temporal columns or vector index in v0). When KB lands its own entity/relation extraction it should register `kb.<type>` entity types and edges via `engenty.server.registerContextGraphSchema(...)` and mirror `knowledge-base.article.{created,updated,deleted}` through declarative `onEvents` bindings, like the contacts pilot in `modules/contacts/src/context-graph-registration.ts`. No code in this module yet. See [context-graph WIP spec](../../docs/content/wip/context-graph/index.md).
- KB AI semantic search uses the synthesized `knowledge_base_article_search` operation (auto-tool from the unified `kb.article` `SearchIndexProvider` registered in `src/plugin.ts`); the underlying `module_kb.search_kb_embeddings` RPC drives the vector path. Keyword/full-text quick lookups go through the same op with `strategy: "lexical"` (BM25/FTS only, no embedder), or via `kb_articles_list` + `search_fts=true` for paginated keyword listings. The hub typing-suggest hot path always pins `strategy: "lexical"`. Re-indexing is event-driven from `knowledge-base.article.{created,updated,deleted}` (declarative `replace`/`delete` bindings on the SDK). Operator backfill / status uses the unified `/api/search-index/providers/kb.article/{status,backfill}` admin surface — there is no module-local `/api/kb/embeddings/*` route. URL-only captures: `POST /api/kb/inbox/:id/fetch-source`; `kb_article_create` is a separate operation from inbox + promote.
- **Dynamic sources** adapter picker merges `GET /api/kb/source-adapters` with `defaultDocumentSourceAdapterRegistry` (`modules/knowledge-base/ui/kb-source-adapters-merge.ts` → `mergeKbSourceAdaptersForPicker`) so built-in adapters (e.g. `firecrawl_url`, label **Firecrawl URL**) always appear; stable order: `url`, `firecrawl_url`, `sitemap`, `web_index`.
- **Source runs** must surface inspectable error text when the backend recorded a failure (adapter context, HTTP status, structured errors) — avoid failed rows with no message.
- After KB source migrations change, run `pnpm db:migrate` locally so Supabase matches the module (see [supabase-workflow.md](../../docs/content/dev/backend/supabase-workflow.md)).

## Editor

- KB article editing ships on **TipTap** (KB rolled back a Plate migration; a Plate package may exist for experiments). Treat Plate as a parallel experiment with Markdown as a bridge, not a drop-in replacement for TipTap JSON in shipped KB flows.

## File storage object folder name

- Knowledge base originals use the file storage folder name **`knowledge-base`** exactly when building keys with `fileStorageTenantObjectKey` from `@engenty/file-storage` (see also `modules/files/AGENTS.md` for general file storage paths).
