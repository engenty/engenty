# Apps

An App is a small program a tenant owns: a frontend, an optional backend, and
its own files. Two things about it are worth holding before anything else.

**It is a folder with a history.** The source is a git work tree on a shared
host directory, not rows in a database. A release is a commit.

**Its two halves never share a disk.** The frontend runs in the viewer's
browser, the backend in an [agentOS](https://rivet.dev/agentos) isolate on
`apps/app-host`. What they do share is one directory on the host, which is the
only thing about an App that survives a deploy.

Everything above the directory is rebuilt on every release. `data/` is not, and

## Where an App lives

One directory per App under `ENGENTY_SPACES_DIR` — `/opt/engenty/spaces` in a
container, `~/.engenty/spaces` in local development. The same value must be set
for `engenty-app-host` and `engenty-ai`; both bind the tree at the identical
path so a directory means the same thing on either side.

| Path | What it is |
| --- | --- |
| `tenants/<tenant>/spaces/<space>/apps/<slug>/src` | the git work tree — the source of truth |
| `tenants/<tenant>/spaces/<space>/apps/<slug>/data` | the App's own files, mounted at `/data` in the isolate |
| `tenants/<tenant>/apps/<slug>` | an App created outside any Space, same two directories |
| `apps/<appHostId>` | a link to the directory above, by App id |

The link exists because a booting replica knows its App id and nothing else. It
is remade on every deploy and on every source write, so an App that moved still
resolves. See `apps/app-host/src/app-store.ts`.

The Space computer binds that Space's `apps/` at `/sandbox/apps`, so an agent
opens `/sandbox/apps/<slug>/src` with ordinary tools and edits the same files
the running App reads. Nothing about that tree is synced to object storage —
see [Agent computers](/docs/dev/agent-computers) for the other mounts a container gets.

Both containers run as uid 1000 because they write the same files. A tree
created by an older, root-running image needs a one-time `chown`.

## A release is a commit

`app_file_write` writes files into the work tree and commits them; the manifest
is written as `engenty.json` beside them. `app_release_propose` commits whatever
is still uncommitted — including edits an agent made from the Space computer —
then reads the tree at that commit and builds it.

A version row is one release attempt of one commit. Postgres keeps only what
git cannot: which commit was released, what it declared, whether it built, and
who approved it.

| Status | Meaning |
| --- | --- |
| `failed` | the commit did not build; `build_log` is what the authoring agent reads |
| `proposed` | built and deployed, waiting for a human |
| `active` | live — exactly one per App |
| `archived` | rejected, or superseded by a later release |

Proposing the same commit twice answers with the version that already exists.
Rolling back redeploys an earlier commit and reuses the document stored at its
release, rather than rebuilding it with a toolchain that has moved on.

Two checks run before a build is attempted, because both are cheaper to fail
here than at an App's first call: an entry the manifest names must be among the
files, and every operation it declares must exist in the registry. Unknown ids
land in the build log by name. See
`modules/engenty-apps/src/domain/release-service.ts`.

The database is `/data/app.db`, opened with the guest's own `node:sqlite`. Under
the hood that is a checkout: `open()` copies the file to a host path and runs
every query there, `close()` writes the whole file back. Two rules follow, and
both are in the app-authoring skill an agent loads before writing one:

- **Open per request, close in `finally`.** The file on disk is only current
  after `close()`.
- **One process owns it.** Apps run at `maxReplicas: 1` for exactly this reason:
  two replicas would be two checkouts of one file.

Native drivers (`better-sqlite3`, `@libsql/client` on a file path) do not load
in the isolate. `node:fs` works on `/data` normally — uploads, exports and
caches go there.

The directory is single-host durability and the only copy of tenant data.
`deploy/scripts/backup-spaces.sh` snapshots it.

## What an App may reach

An App backend never holds a credential. It holds a capability handle: 32 random
bytes with a five-minute life that resolve only in the process that minted them.
The app proxy in `apps/ai` exchanges the handle for the viewing user's token and
calls core's gateway, so an App reaches the whole operation registry — module
operations, core operations, connector actions and the tools of MCP servers —
through one door, as the person using it.

| Gate | Where | What it decides |
| --- | --- | --- |
| Manifest allow-list | app proxy | `engenty.operations`, exact ids, deny-all default. Undeclared means nonexistent. |
| Consent | app proxy | the user approved this manifest's list; a widened list asks again |
| Capability handle | app proxy | resolves to one user and one App, or to nothing |
| The user's own authorisation | core | module policy, tenant scope, connector account — as if the person had called it |
| Approval | core | operations marked `requiresApproval` still pause for a human |

There is no raw REST surface on purpose. An actor token carries a user's entire
grant set and nothing in the codebase narrows one to a list of ids, so a token
in tenant-authored code would be the user's whole session. An exact-id list is
also the only form a human can read and approve.

Because the call runs as the user, there is no autonomous App call: the handle
is minted from a session.

Beside the operations door an App has three smaller stores, all reached through
the same bridge: a **working store** scoped to one artifact instance, **config**
that outlives instances, and declared **Space tables** shared with agents and
people. Records the backend owns outright belong in `/data`; the working store
is scratch.
